# 完成前验证（Evidence Before Claims）

## 触发场景

- 即将说出"完成了 / 修好了 / 测试通过 / 没问题"
- 提交、推送、交付、宣布任务完成的动作之前
- 核对子代理/脚本/自动化工具汇报的"成功"

## 铁律

```
没有新鲜的验证证据，禁止做出完成断言。
```

"应该可以了"不是验证，是猜测穿上了断言的外衣。

## 工作流（门函数，五步）

1. **识别**：什么命令/操作能**证明**这个断言？
2. **执行**：完整跑一遍（新鲜执行，不是引用上次的）
3. **读输出**：看全量输出、退出码、失败计数——不是扫一眼"看起来没红"
4. **核对**：输出确实证实断言？
   - 否 → 如实报告实际状态 + 证据
   - 是 → 断言 + 证据一起说
5. **然后才能**：做出断言

跳任何一步 = 不是在验证，是在说谎。

## 常见断言的验证标准

| 断言 | 必须有 | 不算数 |
|---|---|---|
| 测试通过 | 测试命令输出 0 失败 | 上次跑过 / "应该过" |
| 构建成功 | 构建命令退出码 0 | lint 过了 / 日志看着没报错 |
| bug 修好了 | 复现原症状的用例转绿 | 代码改了 / "改动看起来对" |
| 工具/子代理完成了 | 亲自检查产物（文件在/内容对/diff 对） | 它自己报告 success |
| 需求满足了 | 逐条对照需求清单核验 | 测试过了（测试≠需求） |

## 危险信号（出现即停下先验证）

- 嘴上出现"应该 / 大概 / 看起来"
- 验证之前表达满足（"完美！搞定！"）
- 即将提交/推送但本轮没跑过验证
- 信任子工具的成功汇报
- "就这一次不跑了"
- 累了想赶紧收工——疲惫不是跳过验证的理由，是最需要验证的时刻

| 借口 | 现实 |
|---|---|
| "应该行了" | 跑一下验证 |
| "我很有信心" | 信心 ≠ 证据 |
| "lint 过了" | lint 不等于编译，更不等于测试 |
| "子代理说成功了" | 独立核验它的产物 |
| "部分检查过了" | 部分验证什么都证明不了 |

## 判断基准

- 验证命令的输出要引用关键行（"34/34 通过"、"退出码 0"），不是转述印象
- 回归用例走红绿循环：写用例→过→**撤销修复→必须变红**→恢复→再过——没验过"会红"的回归用例不算回归用例
- agent 汇报的成功一律视为待验证的断言：看文件、看 diff、跑命令
- 本 skill 是所有交付类动作的最后一道门：与 verify 相关的失败教训应回写本表（自我进化）
