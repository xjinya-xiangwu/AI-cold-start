# 发布说明撰写

## 触发场景

- "这版上线了，帮我写更新日志"
- "给用户写一份版本公告"
- "CHANGELOG 怎么写？"

## 工作流

### 第一步：收集原始改动

从提交记录/需求单/测试报告拉出本版本全部改动，逐条标注：

- 类型：新功能 / 优化 / 修复 / 已知问题 / 不兼容变更 / 下线
- 受影响用户：所有 / 部分（哪类）/ 管理员
- 来源需求的用户语言（当时用户是怎么描述这个痛点的）

### 第二步：内外两版分流

**内部 CHANGELOG**（面向团队）：按模块罗列，技术语言可以，全量收录。
**对外 Release Notes**（面向用户）：只保留用户可感知的改动——后端重构、依赖升级、用户无感的内部优化不进对外版。

### 第三步：功能→收益改写（对外版核心）

```
❌ "新增了 RAG 检索优化模块，重构了 embedding 向量化链路"
✅ "搜索快了 3 倍：现在能直接搜到文档里的原话，不用再翻目录"
```

改写规则：动词开头说用户能做什么；数字量化（快了多少/省了几步）；不出现的词：赋能、链路、底层、模块化、优化了若干体验。

### 第四步：分层组织（对外版结构）

```
✨ 亮点（1-3 条，本次最想让用户记住的）
🆕 新功能（功能名 + 一句话收益 + 入口在哪）
♻️ 改进（改了什么 → 用户感受变化）
🐛 修复（只写用户遇到过会搜索的：症状描述，不写代码级根因）
⚠️ 需要注意（不兼容变更/操作迁移步骤，写清"如果你是 XX 用户需要做什么"）
```

### 第五步：诚实度检查

- 已知问题如实列出（写症状+规避方法+预计修复时间），藏问题的发版说明会变成客服工单
- 未全量放开的写清灰度范围（"逐步开放中，没看到请等几天"）
- 版本号遵守语义化：破坏性变更升主版本位，产品无感的技术重构不升

## 输出规范

- 默认同时输出两版：对外 release notes（分层结构）+ 内部 changelog（模块化全量）
- 对外版每条改动必有用户动作或用户感受，纯内部条目移入内部版
- 好的发布说明用户 10 秒能判断"这版跟我有没有关系、要不要更新"——以此为自检标准
