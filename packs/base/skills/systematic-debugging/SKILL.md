# 系统化排查（Systematic Debugging）

## 触发场景

- 任何"不工作"：报错、测试挂、行为反常、性能劣化、构建失败、配置不生效
- **尤其是**：时间紧（紧急让人想猜）、"看起来改一行就好"、已经试过多个修法都没用

## 铁律

```
根因未查明，禁止提出修复方案。
```

第一段没走完，不许开修。症状修补 = 未来故障。

## 工作流（四段顺序执行，不可跳段）

### 第一段：根因调查（任何修复动作之前）

1. **逐字读报错**：不跳过、不略读。报错里常写着答案——行号、路径、错误码
2. **稳定复现**：能可靠触发吗？具体步骤是什么？每次都发生吗？复现不了 → 继续收集证据，不要猜
3. **查最近变更**：什么改动可能引发？diff、近期提交、新依赖、配置变更、环境差异
4. **多组件系统加探针**：跨层链路（前端→API→服务→数据库）在每个组件边界记录进出数据，跑一次看断在哪层，再深入那一层
5. **回溯数据流**：坏值从哪来？谁用坏值调的它？一路向上追到源头，在源头修，不在症状处修

### 第二段：模式对比

- 找同库/同系统里**能跑的类似实现**，对比差异
- 列出每一个差异，再小都列——不许预设"这个不可能有影响"
- 参考实现要**完整读**，略读即埋 bug

### 第三段：单一假设 + 最小验证

1. 假设写成一句话："我认为根因是 X，因为 Y"
2. 用**最小改动**验证，一次只动一个变量——不趁机多修
3. 验证通过 → 第四段；不通过 → **换新假设**，禁止在失败修法上叠加修法
4. 不懂就说不懂，不装懂

### 第四段：实施

1. 先做**最小失败复现**（自动化测试最好，没有就一次性脚本）——修之前它必须失败
2. 只修根因这一处，一次一个改动；禁止"顺手优化"
3. 验证：复现转绿、其他测试没挂、原症状真消失了（衔接 verify-before-done）
4. **修法失败计数**：失败 <3 次 → 回第一段重新分析；**≥3 次 → 停，这是架构问题**——每个修法都暴露新的耦合点/要"大重构"才能做/按下去那边又翘起来，说明方向本身错了。与用户讨论要不要换架构，而不是修第四次

## 危险信号（出现即回第一段）

"先快速修一下回头再查" / "改一下 X 试试看" / "几个改动一起上跑一遍" / "大概就是 X，我直接改" / "我还没完全理解但应该行" / 还没查数据流就开始给方案 / "再试最后一次"（已经失败 2+ 次时）

| 借口 | 现实 |
|---|---|
| 问题很简单，不用走流程 | 简单问题也有根因；流程对简单问题很快 |
| 紧急，没时间走流程 | 系统化排查比瞎试快——瞎试是在付复利 |
| 多改几处一起测省时间 | 无法隔离哪个起效，还引入新 bug |
| 我看出问题了，直接改 | 看出症状 ≠ 理解根因 |

## 判断基准

- 调查真正完成后发现是环境/时序/外部问题：记录查过什么，加重试/超时/监控——但 95% 的"查不到根因"其实是查得不够深
- 线上事故先止损后排查：止血动作走 bug-triage，本 skill 管的是止血之后的根因
- 与 ponytail 互补：梯子说"在根因处修一次"，本 skill 说"怎么找到根因"
