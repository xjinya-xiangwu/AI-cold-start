# 头脑风暴→设计（Brainstorming）

## 触发场景

- "我想做一个 X / 加一个功能 / 改成 Y"——任何创造性请求的起点
- 用户带着模糊想法来，需要先探索再动手

## 硬门

**向用户说明意图并获得批准之前，禁止开始实现**——写代码、搭架子、调实现类工具都不行。仪式随任务大小伸缩，批准门从不缩。

## 第一步：判路径（先说出口，让用户能否决）

- **快验（spike）**：可行性问题（"能不能/行不行/糙点没事"），产出是**答案**不是留用的东西。2-3 句话说明要试什么，得到点头就用最便宜的方式去验证；产出物一律标注"一次性"。终点 = 一条带建议的结论
- **有界（bounded）**：改已存在的东西（新开关、小接口、单文件修复）——判据是**要改的流程已经在那**，不是"我熟悉这类东西"。问关键澄清问题 → 聊天里给短设计（几句到几段）→ **停下等明确同意** → 实现。不写设计文档
- **架构（architectural）**：新项目、新子系统、重组组件关系或改别人依赖的接口。走完整流程：澄清问题（一次一个）→ 2-3 个方案带取舍与推荐 → 分节设计逐节确认 → 落设计文档 → 用户审文档 → 转实现计划

拿不准取**重**的那条。中途发现隐藏复杂度 → 只升不降，停下说明后升级路径。

## 第二步：理解想法（有界/架构路径）

- 先看现状：文件、文档、近期变更——再提问
- 请求包含多个独立子系统（"做个带聊天+存储+计费+分析的平台"）→ 立刻指出需要拆解，别在细节上浪费问题：拆成子项目、理清关系和顺序，然后对第一个子项目走正常流程
- 问题一次只问一个，尽量给选项；聚焦：目的、约束、成功标准

## 第三步：探索方案（架构路径）

- 给 2-3 个不同方案，各自带取舍，推荐项放最前并说理由
- 对每个方案狠用 YAGNI（衔接 ponytail）：砍掉不必要的功能点
- 已有系统里：跟随既有模式；被改动波及的结构问题作为设计的一部分顺手改，不夹带无关重构

## 第四步：呈现设计（按复杂度伸缩）

- 每节长度随复杂度：简单的几句话，微妙的上到二三百字
- 每节呈现后问一句"到这里对吗"
- 覆盖：结构、组件、数据流、异常处理、验证方式
- 单元划分原则：每个单元一个明确用途、接口清晰、能独立理解与验证——"不看内部能不能懂它做什么？改内部会不会破坏使用方？"

## 第五步：落档与批准（架构路径）

1. 设计写入 `docs/specs/YYYY-MM-DD-<主题>-design.md`（或用户指定位置）
2. 自查：占位符（TBD/待定）、前后矛盾、能一处歧义两种解读的要求、范围是否还需拆分——就地修
3. 请用户审文档，改动后重审；批准后才进入实现计划

## 危险信号

| 念头 | 现实 |
|---|---|
| "这太简单，不用对齐设计" | 简单=设计短，不是没有设计。两句话也要批准 |
| "有界，跳过文档" | 用标签跳过工作本身就是疑点——取更重的路径 |
| "设计很显然，他们看着的功夫我先动手" | 门是批准不是阅读时长。展示，然后停 |
| "我熟悉这类应用，所以是有界" | 有界量的是现场，不是你的熟悉度。新项目没有现存流程=架构 |
| "快验的代码能跑，就留着吧" | 快验产出是答案。留用代码是新请求，重新判路径 |
| "变复杂了但快完了，不用重判" | 隐藏复杂度 = 中途升级路径。停下说明 |

## 判断基准

- 与 idea-grilling 分工：那是把模糊想法**问清楚**（要不要做），本 skill 是把已决定的想法**设计出来**（怎么做）
- 批准后不重开争论，但范围变化 >20% 或新暴露风险时重新过门
- 快验的结论要写下来（哪怕一句话），"试过了行不通"是最常丢失的信息
