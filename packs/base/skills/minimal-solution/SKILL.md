# 最简方案梯子（产品版）

## 触发场景

- "这个功能方案是不是做重了？"
- "MVP 应该做到什么程度？"
- "老板说要快，怎么砍？"

## 工作流

### 第一步：先读懂需求再爬梯子（顺序不可反）

梯子压缩的是**方案**，不是**理解**。先确认三件事再动手：真实痛点、目标用户当前替代方案、成功信号。跳过理解直接砍 = 自信地做错。

### 第二步：爬梯子（停在第一个能解决真实问题的档位）

```
1. 这功能需要存在吗？
   痛点证据不足 → 不做，一句话说明观察信号（等什么出现了再做）
2. 配置/规则能解吗？
   运营配置、文案调整、参数修改 → 不写一行代码
3. 已有功能组合能解吗？
   现有功能的搭配/入口调整/流程重排 → 不加新模块
4. 人工流程能先跑吗？
   客服人工处理、表格记录、群里转发 → 先跑两周验证需求真假
5. 最小版本是什么？
   只做主路径（happy path）+ 兜底，一个入口，不做设置页
```

每级输出"**这级为什么不够**"才能升级到下一级——写不出理由的升级是惯性。

### 第三步：不可省清单（砍到这些就是砍残了）

- 数据安全与合规底线（隐私授权、审计日志）
- 信任边界的输入校验（金额、权限）
- 错误兜底（最简版：失败可见 + 可重试，不许静默丢数据）
- 用户明确点名要的核心价值本身
- 灰度/回退开关（没有开关的功能等于不可撤销决策）

### 第四步：输出与标注

- 方案标注已知天花板：`[最简版天花板] 当前方案在 X 场景撑不住（量级），触发条件出现时升级路径是 Y`——最简不等于埋雷不报
- 附"第二版触发器"：什么数据信号出现时启动下一档（如"人工流程周处理量连续两周 >200 单，启动自动化"）

## 判断基准

- 主路径跑通但无兜底 = 不是最简，是残废；兜底做最简版（一句话提示+重试按钮）成本极低
- "以后可能要"不是升级理由，触发器数据才是
- 与 feature-prioritization 分工：优先级决定"先做谁"，本 skill 决定"做多简"

## 输出规范

- 输出：梯子结论（停在哪级+理由）→ 方案描述 → 不可省清单勾选结果 → 天花板标注 + 第二版触发器
- 结束语式样："停在第 4 级人工流程：理由、观察信号、升级触发条件"
- 不输出被砍功能的"完整版设计"——那是触发器触发之后的事
