# 复盘（项目 / 事故）

## 触发场景

- "这期上线翻车了，复盘一下"
- "项目结束了，做个 lessons learned"
- "这次事故写个 postmortem / RCA"

## 选模式（先定，别混写）

- **事故复盘**：线上故障、数据错误、到达用户的缺陷、险情（护栏拦住了但评审漏掉的问题，同样值得写）
- **项目复盘**：里程碑/版本/季度结束的团队反思，写流程与协作，不是单次故障
- 事故进行中不要复盘——先走 bug-triage 止损，复盘是事后动作

## 共同原则（无指责）

- 问"什么条件允许了这件事发生"，不问"谁干的"；需要点名才能讲通的复盘，说明流程有洞
- 每个人在当时掌握的信息下都做了合理决策；改系统，不改人
- 事实与推断分开：时间线只放可核对的事实（日志/告警/消息记录），解释放后面的章节
- 只有当事人记忆支撑的说法标注"凭记忆，未核对"

## 事故复盘工作流

1. **摘要**（2-4 句）：发生了什么 / 影响（用户数、时长、范围）/ 当前状态——只读摘要的人也知道全貌
2. **时间线**：发现→诊断→止血→恢复；标注 TTDR（多久发现）与 TTTR（多久恢复）
3. **根因分析**：5 Whys 追到机制层；主因与促成因素分开列；"每个组件都没错、错在组合"也算根因
4. **响应评估**：什么起了作用 / 什么拖慢了——走弯路的第一次修复要写进文档，尴尬不是删除理由
5. **改进项**：预防型 + 检测型各若干，每条带 owner、期限、验收方式；"调研一下 X"没有 owner 不许进表
6. **险情（near miss）用同一模板**：影响段写"如果没拦住会发生什么"，并标注是反事实推演

## 项目复盘工作流

1. 选框架：做得好 / 做得差 / 想试新（或 Start-Stop-Continue）
2. 原始输入按**主题聚类**，不逐条罗列重复的意见
3. 挑 2-4 个杠杆最高的改进，不是愿望清单；每条变成行动项
4. **回看上次复盘的行动项**：做了没有？不闭环的复盘会让下次没人认真说话

## 判断基准

- 小事故也值得写：模式藏在重复发生的小事里；轻量事故用半页快速模板
- 复盘是历史文档：定稿后不可修改，新发现用带日期的附录追加——改写历史等于伪造记录
- 改进项跟踪到 ticket 才算完成；复盘里全是意向、没有链接，等于没复盘
- 复盘不是干系人状态汇报（那是 product-reporting），也不是追责材料

## 输出规范

- 事故复盘：摘要 + 时间线表（时间/事件）+ 根因与促成因素 + 响应评估 + 改进项表（行动｜类型 预防/检测｜owner｜期限）
- 项目复盘：主题分类 + 行动项表（行动｜owner｜期限｜跟踪处）+ 上次行动项回看
- 轻量事故半页模板：发生了什么 / 时间线 / 根因 / 修复 / 教训
- 与 launch-readiness 的 48h 值守复盘衔接：48h 复盘产出直接套本 skill 模板归档
