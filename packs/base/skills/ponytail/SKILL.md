# 懒人梯子（Ponytail）

## 触发场景

- "帮我加个缓存 / 加个配置项 / 加个抽象层"——先过梯子再动手
- "这也太重了 / 怎么这么多样板代码"
- 用户说"ponytail / 懒人模式 / 最简方案 / YAGNI / 别过度设计"
- 写代码、改代码、选库、做方案——任何"要做一件事"的场合

## 核心立场

懒 = 高效，不是敷衍。最好的代码是没写出来的代码。但梯子**在理解问题之后爬**，不是代替理解——先读完任务涉及的文件、走通真实流程，再开始懒。

## 工作流

### 第一步：爬梯子（停在第一个能站住的横档）

1. **这事需要做吗？** 投机性需求直接跳过，用一行说明为什么不做（YAGNI）
2. **本项目里已经有了吗？** 已有的工具函数/模板/模式 → 复用。最常见的浪费是在三个文件外重写已存在的东西
3. **标准库能做吗？** 能就用
4. **平台原生功能覆盖吗？** 系统自带日期选择器优于引入组件库；数据库约束优于应用层校验
5. **已装的依赖能解决吗？** 能就不新增依赖——几行代码能做的绝不引新包
6. **能一行做完吗？** 一行
7. **以上都不行：** 能跑的最少代码

两个横档都可行 → 取更高的那个（更懒的），继续干。

### 第二步：修 bug = 修根因，不修症状

工单说的是症状。改之前先查这个函数的**所有调用方**——在共享函数里加一个守卫，比在每个调用点各加一个的 diff 更小，而且只修工单提到的那条路径会留着其他兄弟路径照样坏。懒的正确形态 = 在所有流量经过的地方修一次。

### 第三步：输出纪律

- 代码/产物先行，解释最多三行：跳过了什么、什么时候加回来
- 格式：`[产物] → 跳过: X，当 Y 时再加`
- 用户明确要解释（报告/走读/阶段说明）时给全——规则禁止的是没被要求的散文，不是被要求的交付

### 强度三档（用 "ponytail lite/full/ultra" 切换，默认 full）

| 档 | 行为 |
|---|---|
| lite | 按要求做，但用一行指出更懒的替代方案，用户选 |
| full | 梯子强制执行：标准库优先、最短 diff、最短解释 |
| ultra | YAGNI 极端派：删除优先于新增。交付一行方案，并在同一句里质疑需求的其余部分 |

## 判断基准

- 不做未经要求的抽象：只有一个实现的接口、只有一个产品的工厂、给不变的值做配置——都禁止
- 删除优先于新增；无聊优于聪明——聪明是别人凌晨三点要破译的东西
- 文件越少越好；最短可用 diff 获胜——但前提是理解了问题，错误位置的最小改动是第二个 bug
- 刻意走捷径且有已知天花板的（全局锁/O(n²)/朴素启发式），用 `ponytail:` 注释标明天花板与升级路径
- 非平凡逻辑（分支/循环/解析/资金安全路径）留一个最小可跑的检查——逻辑坏了它就失败的那种；一行小改动不需要测试，YAGNI 对测试同样适用

## 永不偷懒清单

信任边界的输入校验、防数据丢失的错误处理、安全措施、无障碍基础、用户明确要求的东西——用户坚持要完整版就做完整版，不再争论。
