# 风险登记与跟踪

## 触发场景

- "这个项目有哪些风险？"
- "帮我建一个风险清单"
- "上次延期的事怎么就没提前发现？"

## 工作流

### 第一步：识别（结构化挖掘，不靠头脑风暴灵感）

从五个来源系统性挖，每来源至少过一遍：

1. **依赖**：外部团队/供应商/合规审批——每个依赖问"晚到两周会怎样"
2. **技术**：没做过的东西（新架构/新集成/性能要求）——"哪里最可能超预期"
3. **人员**：单点依赖（某人休假项目停摆）、团队新领域
4. **范围**：需求边界模糊处、未书面确认的口头承诺
5. **外部**：平台政策、季节流量、竞品动作

### 第二步：登记表与定级

```
R#  风险描述(条件→后果)  类别  概率(高中低)  影响(高中低)  等级  应对策略  Owner  触发器  状态
```

- 风险描述必须是"**如果 X 发生，则 Y 后果**"格式（"技术风险"不是风险，是分类）
- 等级 = 概率 × 影响（高×高=红 / 任一高=黄 / 双低=绿）
- **触发器**是本表与普通风险清单的核心差异：每条风险写明"出现什么信号说明它正在发生"（如"联调环境第二次延期"），没有触发器的风险无法预警

### 第三步：应对策略四选一（每条必选）

| 策略 | 适用 | 示例 |
|---|---|---|
| 规避 | 改方案绕开 | 砍掉依赖不成熟的功能 |
| 缓解 | 降概率或降影响 | 提前 POC、备份数据、并行供应商 |
| 转移 | 交给更能扛的人 | 合同条款、保险、外包保障 |
| 接受 | 代价小或无法处理 | 低影响风险记录在案即可 |

红色风险必须配缓解动作 + 动作 owner + 完成时间；"接受"仅限绿/黄级。

### 第四步：跟踪节奏与复盘

- 周会过一遍风险表（5 分钟）：状态变化、新增风险、触发器信号
- 每个触发器命中或风险兑现后做一次小复盘：信号是否够早、应对是否生效
- 项目结束时全表复盘：兑现的风险（预警是否有效）、未兑现的（高估还是缓解见效）、漏掉的（从哪类来源补识别）

## 判断基准

- 风险表 <5 条 = 挖掘不充分，回到五个来源再过一遍
- 全是技术类风险 = 通常漏了人员与依赖类（最常见的延期真因）
- 红色风险没有 owner 和缓解动作 = 风险表沦为形式，逐条补齐

## 输出规范

- 主交付是登记表（全字段），不是风险散文
- 新项目场景与 project-kickoff 联动：启动时的首次登记 ≥3 条，之后本 skill 负责持续跟踪
- 复盘输出"来源清单补丁"：本次漏掉的风险属于哪个来源，下次识别先查它
