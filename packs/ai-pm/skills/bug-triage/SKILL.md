# Bug 分级与响应

## 触发场景

- "线上出问题了，这事算 P 几？"
- "客诉/工单涌进来了，先处理哪个"
- "这个 bug 现在就修，还是排下个版本"

## 工作流

### 第一步：分级（影响面 × 严重度）

| 级 | 定义 | 典型特征 |
|---|---|---|
| P0 | 主流程不可用 / 资损 / 数据错误 / 安全问题 | 核心功能全挂、下单失败、余额算错 |
| P1 | 核心功能受损但有绕行方案，或影响面受限 | 关键功能间歇失败、特定人群不可用 |
| P2 | 非核心功能异常 / 体验明显劣化 | 展示错误、偶发卡顿、次要链路故障 |
| P3 | 轻微问题 / 瑕疵 | 文案错别字、样式小瑕疵 |

- 判断顺序：先影响面（多少用户 × 是否主路径），再严重度（资损/数据 > 功能 > 体验）
- 有争议时定级就高不就低：定错了降级容易，升级慢了代价大
- 提测/测试阶段的 bug 复用同一矩阵，"阻塞主流程验收"视同 P1

### 第二步：响应时限与升级（定级即触发，不商量）

- P0：10 分钟内响应、拉应急群，1 小时内给出止血决策；半小时无头绪立即升级
- P1：1 小时内响应，当天下止损结论
- P2：24 小时内响应，排入下个版本
- P3：排入日常队列，不设强时限
- 升级规则：预计修复时间超过时限一半、或影响面扩大一档，立即升级并扩群——不要"再自己试十分钟"

### 第三步：止损优先于根因（分钟级动作库）

止血动作按代价从低到高选：

1. 关灰度 / 关功能开关（有开关的功能首选）
2. 回滚到上一版本（可回滚性在 launch-readiness 已验证）
3. 公告 + 客服话术（止不了血先管理预期：已知问题 / 预计恢复 / 绕行方案）
4. 数据修复预案（涉及资损或数据错误的，先冻结再修）

- 根因排查放在止损之后：P0 现场只回答"能不能止血"，不回答"为什么会这样"
- 修完不等于结束：P0/P1 处置完 48 小时内转 post-mortem，改进项防复发

### 第四步：降级与疑似处理

- 同类反馈 ≥3 个独立来源 → 升半级观察；只有 1 个来源且无法复现 → 标"待复现"，追线索（环境/版本/时段）
- 复现步骤、报错信息、影响时段三样凑不齐的，按"疑似"挂低半级，不占高优队列

## 判断基准

- "用户骂得凶" ≠ 高级别：先换算成影响面与严重度；情绪不参与定级，但客服话术要跟上
- 止损越早，现场越难保、根因越难查——接受这个代价，业务先活下来
- 定级标准写进团队 wiki，且每次 P0 后回看一次：定级争议本身就是一个流程改进项

## 输出规范

- 输出：定级结论（级别 + 一句话依据）+ 响应动作（谁 / 何时做什么）+ 止血选项（按代价排序）+ 升级条件
- P0/P1 处置完 48 小时内转 post-mortem；与 launch-readiness 的值守清单、risk-register 的红色风险共用升级机制
