# 反馈分诊与需求池管理

## 触发场景

- "这 50 条用户反馈帮我整理一下"
- "群里的反馈 / 商店的差评怎么处理"
- "这些反馈哪些值得做成需求"

## 工作流

### 第一步：归一收集（所有渠道进同一张表）

- 字段：来源（工单/群聊/商店评论/访谈/销售带回）、用户身份（角色/付费层级/活跃度）、原话、时间
- 原话保留原样不改写；解读另起一列——把客气话和吐槽都还原成"场景 + 诉求"

### 第二步：去重聚类（先聚类，再谈优先级）

- 按"用户想达成什么"聚类，不按功能模块聚类——同一痛点会以十种功能抱怨的形态出现
- 每个主题记：独立用户数、来源渠道数、最早/最近出现时间
- 渠道越多越真：三个渠道都在抱怨同一件事，比一条反馈重读十遍更可信

### 第三步：四问分诊（每个主题过一遍）

1. **是谁**：高频用户还是新用户？付费大客户还是免费散客？——身份决定权重，不决定对错
2. **什么问题**：是 bug（体验坏了）还是需求（现有方案不够）还是误解（信息没传到）？
3. **多痛**：绕行成本多高？是不是每次都要手动绕？
4. **多频**：一次性抱怨，还是每周必发生？

### 第四步：分级路由（分诊后各回各家）

- **是 bug** → 转 bug-triage 定级响应；不要在需求池里修 bug
- **是需求** → 写需求卡片（见第五步），进池子等 feature-prioritization 统一打分
- **是误解** → 不是产品问题，是文案/引导问题——同样建卡交给体验侧修
- **是情绪宣泄 / 无信息量** → 归档不计入统计，别让噪音抬高某个主题的声量

### 第五步：需求卡片化（进池子的准入证）

- 必填：场景（谁在什么情况下想做什么）/ 诉求（现在怎么痛）/ 证据（N 个独立用户、来源渠道、典型原话 1-2 条）/ 已试过的绕行方案
- 证据不足的卡标"待验证"，优先放进下次访谈求证（见 user-research-interview），不许直接进排期
- 卡片只写问题不写方案——方案是 feature-prioritization 之后的下一步

## 判断基准

- 声量大 ≠ 优先级高：分诊负责给证据，排序交给 feature-prioritization 的 RICE/WSJF
- 需求池不是垃圾桶：超过一个季度没动且没有新增证据的主题，标"沉睡"并知会提交人
- 反馈闭环要有回音：转需求了 / 不做的理由 / 修好了——反馈人收不到回音，下一次就不再反馈
- 客服解决的每个 bad case 回填一行到需求池：这是需求池的主要进水口，也是最容易被忽略的一条

## 输出规范

- 输出：主题聚类表（主题/独立用户数/渠道数/典型原话）+ 每主题分诊结论（路由去向）+ 需求卡片若干
- 与 bug-triage、feature-prioritization、user-research-interview 明确衔接：分诊是路由器，不是终点
