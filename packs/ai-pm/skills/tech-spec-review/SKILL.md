# 技术方案评审（PM 版六问）

## 触发场景

- "开发给的技术方案，我看得半懂，怎么提意见？"
- "明天技术评审会，我该问什么？"
- "这个方案感觉有点问题但说不上来"

## 工作流

### 第一步：先审懂的部分（不用装懂代码）

技术方案里 PM 必须完全看懂的段落：**背景与目标、用户影响、接口约定（输入输出）、上线计划**。这些看不懂 = 让开发重写到能看懂（这是合理要求，不是外行要求）。看不懂的部分先列出，评审会上逐个确认。

### 第二步：六问逐个过（每问都有"开发答不上 = 风险"的判断）

**Q1 异常处理**：失败了会怎样？
- 追问：超时怎么办？依赖的服务挂了怎么办？用户会看到什么？
- 答不出 = 只设计了 happy path，异常流回炉

**Q2 边界条件**：极端情况呢？
- 追问：数据量为 0 / 超大时会怎样？并发同时操作同一条数据？老数据没有新字段？
- 答不出 = 上线后第一批线上问题来源

**Q3 数据一致性**：两个系统数据对不上怎么办？
- 追问：写 A 成功写 B 失败？以哪个为准？用户看到的是哪个？
- 涉及钱、库存、权限时此问不过 = 阻塞级问题

**Q4 回滚方案**：出问题怎么退回来？
- 追问：回滚会不会丢用户数据？新表结构能兼容旧版本吗？回滚要多久？
- "到时候再说" = 上线前必须补

**Q5 监控与告警**：怎么知道它坏了？
- 追问：什么指标异常会报警？谁收到？多久发现？
- 没有监控的功能 = 坏了靠用户投诉发现

**Q6 容量与性能**：量上来会怎样？
- 追问：预估峰值多少？超过预估的 10 倍呢？哪里最先崩？
- 不要求精确数字，要求开发"想过"

### 第三步：把回答转成行动项

评审产出的每个"答不上/待确认"进入待办清单：**问题、责任开发、期望答复时间、阻塞上线与否**。六问全过的方案才进排期。

## 判断基准

- 开发说"这个细节实现时再定"：实现细节可以，**六问的答案不可以**——它们是方案级承诺
- PM 不需要懂代码，但需要坚持把答案翻译成自己能复述的话——复述不出来就是没答清
- 评审不是考试：六问是协作工具，帮开发自查盲区，不是挑刺表演

## 输出规范

- 输出：六问逐条结论（✅已答清 / ⚠️待确认+期限 / ❌阻塞项）+ 待办清单
- 评审会前把这个清单发给开发，会上只过 ⚠️ 和 ❌
- 与 prd-review 组合：PRD 层面问题先在 prd-review 清掉，避免技术评审会被需求问题稀释
