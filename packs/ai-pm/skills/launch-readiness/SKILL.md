# 上线就绪检查（Go / No-Go）

## 触发场景

- "周四要上线了，帮我过一遍检查"
- "上线前都要确认什么？"
- "上次上线客服被打爆，这次怎么防"

## 工作流

### 第一步：六维检查单（逐项 ✅/❌，❌ 须有 owner 和期限）

**① 功能**：验收标准全过（对照 dev-handoff 交接包逐条）｜主路径手动走通一次｜灰度开关可用且有人有权操作

**② 数据**：埋点上线且能查到（不是"会有的"）｜报表/看板就位｜数据迁移脚本已演练（不是首次在生产跑）

**③ 回滚**：回滚方案演练过｜回滚是否丢数据的结论明确｜回滚决策人+授权明确（半夜不用开会找人）

**④ 监控**：核心指标告警配置（错误率/延迟/业务量）｜告警接收人在线｜异常基线心里有数（上线后涨多少算正常）

**⑤ 用户侧**：客服话术就绪（新功能怎么用/常见问题）｜用户可见文案终审（错别字检查）｜FAQ/帮助文档同步更新

**⑥ 灰度**：放量计划（比例阶梯与观察间隔）｜每一档看什么指标、达标条件、恶化时的回退动作

### 第二步：go/no-go 判定

- 六维全 ✅ → go
- ③④ 任一 ❌ → **no-go**（无回滚无监控的上线是赌博，没有例外）
- 其他维度 ❌ → 条件 go：列出补齐期限，且责任人在上线窗口前书面确认

### 第三步：上线后 48 小时值守清单

```
T+1h：主路径+核心指标人工巡检（对照基线）
T+24h：灰度放量决策（对照放量计划）
T+48h：复盘会（实际 vs 预期：指标、事故、客服工单类型）
```

值守期间任何 P0 问题走 bug 分级响应，止损优先于根因（先关灰度再查）。

### 第四步：上线复盘归档

48 小时复盘产出：实际指标 vs 预期、检查单漏项（哪个维度低估了）、下一版检查单补丁。检查单是活的，每次事故回来加一条。

## 判断基准

- "来不及演练回滚" = no-go 的标准答案，功能晚两天上线没有代价，事故有
- 灰度不是保险柜：没定放量指标的灰度只是慢速赌博
- 大促/节假日前窗口默认冻结或双倍谨慎（流量异常时最难排障）

## 输出规范

- 输出：六维检查表（逐项状态）+ 判定结论 + 值守清单 + 复盘归档模板
- 检查表直接引用 dev-handoff 交接包与 experiment-design 的指标定义，不重复发明口径
- 上线后补一条纪律：检查单漏项必须回写本 skill 的检查表（自我进化机制）
