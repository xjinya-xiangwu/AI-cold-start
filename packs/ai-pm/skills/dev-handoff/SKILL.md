# 需求交接包（Dev Handoff）

## 触发场景

- "PRD 评审过了，怎么交给开发？"
- "开发总来问细节，是不是我 PRD 没写清楚"
- "联调时才发现两边理解不一样"

## 工作流

### 第一步：交接包清单（七件套，缺一件就是一个来回）

```
1. 验收标准（最重要，逐条可测试）
   格式：给定[条件]，当[操作]，则[可观察结果]
   例：给定未登录用户，当点击收藏，则弹出登录引导且不丢失当前页面
2. 正常流 + 异常流（每类异常的处理策略）
3. 边界与老数据（数据迁移/兼容规则/为空处理）
4. 埋点需求（事件名+属性+触发时机，附口径）
5. 灰度与开关（灰度比例、放量条件、谁有权关）
6. 依赖与联调约定（接口谁出、mock 时间点、联调环境）
7. 开放问题的边界（哪些点允许开发自行决定——写出来，不写就是默认都不允许）
```

### 第二步：三问自查（交出去前）

1. **新人测试**：一个不了解背景的开发只看交接包，能说出这个功能"解决谁什么问题"吗？
2. **验收测试**：测试拿到验收标准，能直接写用例吗？（写不出用例的验收标准重写）
3. **反例测试**：故意挑一条异常流问自己"开发知道怎么办吗"——不知道 = 补进交接包

### 第三步：交接会的 15 分钟

1. 开发**当场复述**验收标准（发现理解偏差最便宜的时刻）
2. 逐条过异常流与开放问题，现场定掉能定的
3. 约定联调时间点与提测标准（提测 = 七件套里的 1、2 满足）

### 第四步：交接后的变更纪律

- 需求变更必须**书面**同步交接包（改哪段、为什么、影响谁），口头变更 = 下一次扯皮的种子
- 变更记录附在交接包末尾（日期/变更/原因/通知到谁），复盘扯皮时回看

## 判断基准

- 开发第三轮还来问细节：不是开发笨，是交接包有洞——把问题补进包里并更新，不是再口头解释一遍
- "开发自己会想到的"是最贵的假设：埋点和灰度几乎从来不会被主动想到，必须显式交付
- 七件套齐但开发仍复述不出验收标准 = 交接会没开成形式，重开

## 输出规范

- 主交付：七件套交接包文档 + 变更记录区
- 与 prd-drafting 分工：PRD 面向评审决策（why 为主），交接包面向实现（how 精确到可测试）；从 PRD 生成交接包时逐条转写验收标准，不复制粘贴段落
- 交接完成标志：开发在交接包上确认"无未答复问题"
