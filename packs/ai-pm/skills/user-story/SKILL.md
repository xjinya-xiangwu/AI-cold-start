# 用户故事与场景设计

## 触发场景

- "帮我写用户故事 / 拆一下需求"
- "这个功能的用户场景有哪些"
- "画一下用户旅程"
- 敏捷开发需求的 user story 编写

## 核心格式

```
作为 <具体角色>，
我想 <完成什么任务（不是"使用什么功能"）>，
以便 <获得什么价值>。

验收条件：
- Given <前置状态> When <用户动作> Then <系统行为+可见结果>
（每个故事 2-5 条验收条件，覆盖正常流+至少 1 条异常流）
```

**关键区分**：故事写"任务"不写"功能"。
- ✅ "我想在客户抱怨时 10 秒内找到他去年的投诉记录"
- ❌ "我想使用搜索功能"

## 工作流

### 第一步：角色盘点（先于故事）

列出所有会接触该产品的角色（不止终端用户）：

终端用户 / 管理员 / 运营人员 / 审核人员 / 对接系统 / 合规与法务 / 老板（看数据的人）

每个角色问三个问题：TA 的高频任务是什么？TA 最怕什么（搞砸的代价）？TA 怎么判断这事做成了？

### 第二步：场景采集

从四个来源找真实场景，避免闭门造车：

1. 用户访谈/客服记录中的原话（"我上次想……结果……"句式是金矿）
2. 现有流程的 workaround（用户在用 Excel/群聊/人肉补的环节 = 最强需求信号）
3. 极端场景：数据量最大的一天、最不懂的用户、最坏的网络
4. AI 产品特别地：**用户第一次用（cold start）**和**第一百次用（惯性使用）**是两个故事

### 第三步：故事拆分与优先级

- 按 INVEST 检查：Independent（可独立交付）/ Negotiable（可讨论实现方式）/ Valuable（对用户有价值）/ Estimable（可估）/ Small（够小）/ Testable（可测）
- 一个故事一个迭代内能完成；写不下就拆
- 优先级 = 用户价值 × 使用频率 ÷ 实现成本，标注在每条故事旁
- MVP 边界：明确列出"第一版不做"的故事清单（比"做什么"更能防止范围蔓延）

### 第四步：AI 功能故事的特别检查

AI 功能的用户故事必须额外覆盖：

1. **不确定性故事**：AI 答错了，用户故事是什么？（纠正/重试/兜底/放弃）
2. **信任建立故事**：第一次用怎么让用户敢用？（展示来源/解释能力边界/可试金石的示例）
3. **人机接力故事**：AI 干到哪一步人接手？交接物是什么？
4. **空状态故事**：知识库没数据/模型没配置时用户看到什么？

## 输出规范

- 故事地图先行：横轴用户旅程阶段，纵轴优先级，先给全景再给细节
- 每条故事带编号（US-001），供后续追踪
- 异常流验收条件不可省略——只写正常流的故事在 AI 产品里等于没写
- 结尾输出"未决问题"：哪些故事依赖业务方/算法侧的未定事项
