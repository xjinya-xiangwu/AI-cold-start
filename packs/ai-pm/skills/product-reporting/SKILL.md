# 产品汇报（周报 / 月报 / 季度）

## 触发场景

- "帮我写这周的周报" / "月度总结" / "季度汇报"
- "把这些进展整理成给老板看的 update"
- "管理层要一份项目健康度摘要"

## 工作流

### 第一步：定档位与受众（不确定就默认管理版）

- 周报：具体事项+数据+下周计划；月报：趋势+里程碑+战略对齐；季度：目标达成度+结论与下季建议
- 受众只分两档：**管理版**（结论先行、≤300 字、只留需要他决策或知晓的事）与**协作版**（细节、依赖、需要对方做什么）

### 第二步：RAG 健康度 + 一句话理由

- 🟢 正常推进 ｜ 🟡 有风险但有预案 ｜ 🔴 脱轨需要干预
- 🟡 不是失败，是风险管理：第一信号出现就升黄，不要等确认恶化才报
- 🔴 必须写清"我已经试过什么、现在需要什么"，只报灾不给出路等于把问题原样上交

### 第三步：四段式正文

1. **进展**：写结果不写活动。"上线了 X、留存 +1.2pt"可以，"开了 4 个会、修了 23 个 bug"不行
2. **数据**：每个数字带口径与对比基线（环比/目标）；无口径数字不入汇报（见 metric-design）；数据异常必给下钻结论或注明"正在查"（见 data-insight）
3. **风险**：风险+影响+缓解+owner 四件套；自己能兜住的小风险不写，除非需要知情
4. **求助**：每条是具体到人和期限的请求——"需要 X 决策，建议选 A，周五前"，不是"需要支持"

### 第四步：头部 TL;DR（管理层 30 秒版本）

- 一句话：健康度 + 最重要的一件事
- 需要决策的问题放 TL;DR 之后的第一个位置；坏消息放在好新闻前面，不藏

### 第五步：按受众改写（同一事实多种讲法）

- 对老板：结果与目标对齐，砍掉实现细节和工单号
- 对协作方：写"对你有什么影响、需要你做什么、什么时候要"
- 版本切换不改事实，只改高度与详略

## 判断基准

- 汇报是决策输入，不是流水账：数字必须可复算（口径+基线）
- 隐瞒延误的信任成本远大于报黄的尴尬；报黄要趁早，选项才会多
- "开了几个会"不是进展；用户可感知的变化才是
- 没有求助就删掉该段，不凑格式；只有风险没有缓解措施的风险不上表

## 输出规范

- 输出：TL;DR（1-2 句）+ RAG + 四段式正文；管理版 ≤300 字
- 数据段引用 data-insight 的归因结论，风险段可引用 risk-register 的登记项，不自造口径
- 上次汇报的求助项没闭环的，本次开头先交代结果——open loop 会让汇报失去信誉
