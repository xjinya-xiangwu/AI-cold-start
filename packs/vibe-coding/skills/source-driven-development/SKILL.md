# 文档驱动开发：一切以官方文档为据

凭记忆写框架代码 = 用训练数据里**可能已过时**的模式写正确性要紧的东西。这一技能强制每个实现决定**对齐官方文档**，并留下出处引用。

## 核心循环

1. **决定要验证什么**：这次实现依赖哪个框架行为？（如"这个钩子的触发时机""这个参数的默认值"）
2. **查官方文档**：优先官方文档站 → 官方 GitHub 仓库（源码/测试）→ 官方博客。**三方博客与 AI 记忆不算权威**，只能当线索。
3. **版本对齐**：确认文档版本 = 项目实际依赖版本（锁文件里那个）。文档领先或落后一个版本，行为可能完全不同。
4. **带出处实现**：代码注释/提交信息里留下文档链接；关键行为标注"依据 vX.Y 文档 §某节"。
5. **文档缺失或冲突时**：写最小验证脚本实测行为，把实测结论当事实源并注明。

## 什么时候必须走这一步

- 用不常写的 API（一年碰一次的那种，记忆最不可靠）
- 框架大版本升级后的第一次实现
- 行为"应该是 X 吧"——每次心里冒出"应该"就查一次
- 安全、支付、数据迁移等**出错代价高**的路径

## 什么时候可以跳过

- 项目内自有代码与既有惯例（这才是你该对齐的本地事实源）
- 语言基础语法（for 循环不需要查文档）
- 已在本项目验证过的模式（第一查过之后记录下来即可复用）

## 抗模式

- **训练数据过时**：AI 记忆里的 API 在三年间换了签名、改了默认值、标了废弃。
- **博客搬运**：三方教程省略边界条件，照抄埋雷。
- **只查不引**：查了但没留出处——三个月后没人（包括你自己）知道这个行为为什么这样写。
