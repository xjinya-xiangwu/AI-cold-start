# 五轴代码评审

每处变更合并前必过评审——包括自己写的和 AI 生成的一切。五轴：正确性、可读性、架构、安全、性能。通过标准：**这次变更确实让代码库整体更健康**，而非完美无缺。

## 评审前先懂上下文

- 这次变更想完成什么？依据什么规格？预期行为变化是什么？
- **先读测试**：测试存在吗？测的是行为还是实现细节？边界覆盖了吗？改名重构会不会让它们变红？

## 五轴逐项过

**正确性**：与规格一致？边界（空/空边界/并发/状态不一致）处理了吗？错误路径处理了还是只有 happy path？

**可读性**：陌生工程师不问作者能看懂吗？命名与项目惯例一致？有无该拆的深嵌套与"聪明技巧"？**1000 行里 100 行够用就是失败**。

**架构**：跟随既有模式还是引入新模式（新模式要有理由）？模块边界干净？依赖方向正确？重构是**降低**复杂度还是只是搬家？

**安全**：用户输入校验与净化？秘密不进代码/日志/版本库？查询参数化（禁止拼接）？外部数据当不可信处理？

**性能**：N+1 查询？无界循环/无分页全量拉取？热路径里造大对象？

## 发现分级（每条标注，作者才知道哪些必改）

| 前缀 | 含义 |
|---|---|
| Critical | 阻断合并：安全漏洞、数据丢失、功能损坏 |
| （无前缀） | 必改：合并前处理 |
| Nit | 可选：格式与风格 |
| Consider / FYI | 建议或仅背景 |

排序按杠杆：正确性与安全 → 结构问题 → 其余。**一个结构问题比十条琐碎更有价值**。

## 验证的验证

- 跑了哪些测试？构建过了吗？改了 bug 就同时评审修复**和回归测试**。
- "测试都绿了"只是必要条件——绿测试抓不到架构问题和可读性问题。

## 红线

- 不盖章式 LGTM（没有证据的通过帮倒忙）。
- 不软化真问题（"可能有点小问题"掩盖的是上线会炸的 bug）。
- 大变更要求拆分，而不是硬着头皮"大概看完了"。
