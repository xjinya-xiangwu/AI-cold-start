# 测试场景生成

把一句用户故事拆成可执行的场景清单：每条场景=目标+前置+角色+步骤+预期。交付物是 QA 拿到就能跑的文档。

## 七步流程

1. **审读用户故事**与验收标准——故事里每个"能/可以/应该"都是一条场景种子。
2. **定义测试目标**——这条场景到底验证什么行为？一句话说不清就是还没想清。
3. **建立起始条件**——系统要处于什么状态、要什么数据、什么配置。前置条件写不清，场景就不可复现。
4. **指定用户角色**——谁执行这些操作（买家/管理员/访客）。权限差异就是测试差异。
5. **拆分测试步骤**——每步一个动作加一个可观察结果；"看到"和"系统做了"要分开写。
6. **写预期结果**——必须是**可观察**的（页面元素/接口返回/状态变化），不写"工作正常"这类空话。
7. **补边界与错误场景**——非法输入、边界值、并发、超时、权限不足、依赖不可用。

## 场景模板

```
测试场景：[一句话名称]
测试目标：[验证什么]
起始条件：[系统状态 / 数据 / 权限]
用户角色：[谁操作]
测试步骤：
1. [动作] → [预期观察]
2. ...
预期结果：
- [可观察结果 1]
- [可观察结果 2]
```

## 边界场景清单（逐项过一遍）

- 空输入 / 超长输入 / 特殊字符 / 非法格式
- 边界值（0、负数、最大值、差一位越界）
- 重复提交 / 并发操作 / 中途取消
- 权限不足 / 会话过期 / 依赖服务不可用
- 数据不存在 / 已被删除 / 状态冲突

## 红线

- 每条场景必须有**可观察**的预期结果，禁止"运行正常""符合预期"。
- 起始条件含糊的场景等于没写——换台机器必须能复现。
- 覆盖率数字不是目标，**行为覆盖**才是：每个验收标准至少一条场景。
