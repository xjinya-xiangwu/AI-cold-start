# 规格驱动开发：先规格，后代码

没有规格就写代码 = 猜。规格是人与人、人与 AI 之间的**共同事实源**：定义我们在建什么、为什么建、怎么算建完。

## 规格最小结构（五问）

1. **问题**：要解决什么问题？给谁解决？（一句话说不清 = 还没想清）
2. **范围**：做什么 / **明确不做什么**（不做清单比做清单更能防 scope creep）
3. **方案概要**：怎么做（数据流/接口/关键决策），以及**考虑过并放弃的替代方案**（防三个月后重复踩坑）
4. **验收标准**：可验证的"完成定义"——每条都要能变成一条测试或一次检查
5. **风险与未决**：已知的不确定项、需要谁拍板的问题

## 工作流

1. 动手前先写规格初稿（AI 可以根据对话代拟，人负责修正）。
2. 与所有相关方对读一遍——规格阶段改一句话，实现阶段省一天。
3. 规格定稿后作为事实源提交（进仓库、进 issue，别只躺在聊天记录里）。
4. 实现过程中规格变更 → **先改规格再改代码**，保持两者同步。
5. 完成时逐条对照验收标准销项。

## 抗模式

- **规格膨胀**：把实现细节（类名/函数签名）写进规格——规格定义 what，how 留给实现。
- **一次定终身**：写完就锁死不再更新——与现实脱节的规格比没有更危险。
- **AI 直出不做**：AI 代拟的规格必须逐条人工核——它会把没确认过的假设写得像已经决定。
