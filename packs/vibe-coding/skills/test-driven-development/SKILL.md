# 测试驱动开发（TDD）

红 → 绿循环。TDD 的价值不在"有测试"，而在循环产出的测试**值得保留**。

## 好测试长什么样

- 测**行为**，不测实现细节：代码可以整个重写，测试不该跟着改。
- 好测试读起来像规格说明："合法购物车可以结账"——一眼看出系统能力。
- 期望值来自独立事实源：已知常量、规格文档、手算示例。**绝不用被测代码自己的算法重算期望值**（同义反复测试永远绿，永远抓不到 bug）。

## 接缝（Seams）：测试写在哪

- **接缝** = 不进入内部就能观察行为的公开边界。
- 只在约定好的接缝上写测试；动手前先列出接缝清单并确认。
- 每个接缝标注：能抓到什么、抓不到什么（例如 HTTP API 层能抓到路由与校验回归，抓不到纯函数内部的边界）。

## 循环规则

1. **红灯先于绿灯**：先写失败的测试，再写恰好让它通过的实现。不为未来的测试预留、不加投机功能。
2. **一次一个切片**：一个接缝、一个测试、一份最小实现，循环推进。
3. 每个测试都是**曳光弹**：回应上一个循环学到的东西，而不是预先铺满。

## 抗模式（出现即返工）

- **实现耦合**：mock 内部协作对象、测私有方法、绕过接口查数据库——重构一开测试就红，就是这类。
- **同义反复**：断言用代码同款逻辑重算期望值，永远通过、永远无意义。
- **横切切片**：先写完所有测试再写所有实现—— bulk 测试验证的是想象中的行为。改成垂直切片：一测一实现循环。

## 边界情况

- 每个切片都考虑：空输入、边界值、非法输入、并发与超时。
- 测试失败时，先怀疑测试本身（是否测错了行为），再怀疑实现。
