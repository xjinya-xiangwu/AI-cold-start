# 六条编码行为准则

源自 Andrej Karpathy 公开分享的 LLM 编码观察（出处见文末），改造为本包通用的行为纪律。每次写代码前过一遍，写完后对照验收。

## 1. 先想清楚，再动手（Think Before Coding）

- 动手前把假设**写出来**；不确定就问，不要闷头猜。
- 存在多种理解时摆出来让用户选，不要默默挑一个。
- 有更简单的做法就说出来，必要时据理力争。

## 2. 简单优先（Simplicity First）

- 用**解决问题的最少代码**。没有要求的功能不做；只有一个使用场景就不做抽象。
- 不写没人要的"灵活性"和"可配置"；不为不可能的场景写错误处理。
- 自检：如果 200 行能写成 50 行，重写。"资深工程师会不会觉得这过度设计了？"

## 3. 外科手术式修改（Surgical Changes）

- 只改必须改的；不顺手"优化"相邻代码、注释和格式。
- 不重构没坏的东西；匹配周围代码的写法，哪怕你有别的偏好。
- 每一行改动都应能追溯到需求。自己的改动产生了孤儿代码就清理；**既有死代码指出来，不经允许不删**。

## 4. 目标驱动执行（Goal-Driven Execution）

- 把任务转成**可验证的目标**："加校验" → "写非法输入的测试，让它通过"。
- 多步任务先列计划：`1. [步骤] → 验证: [检查]`，逐条闭环。
- 验收标准弱（"让它能用"）会逼你反复追问；强标准让你独立跑完。

## 5. 测试值得保留（What a Good Test Is）

- 测试走**公开接口**，不测实现细节——重构后测试不应坏。
- 好测试读起来像规格说明："合法购物车可以结账"。
- 断言的期望值来自独立事实源（已知常量/规格/手算），**不要用代码自己的算法重算期望值**（同义反复测试永远绿，永远没用）。

## 6. 红灯先于绿灯（Red Before Green）

- 先写失败的测试，再写恰好让它通过的实现。
- 一次一个切片：一个接缝、一个测试、一份最小实现。
- 重构不属于红绿循环——它属于评审阶段，循环里只做让测试变绿的最小改动。

## 红线

- 不为想象中的未来需求写代码。
- 不在功能提交里夹带重构（分开提交）。
- 宣称"完成"之前必须给出验证证据（测试输出/运行结果）。
