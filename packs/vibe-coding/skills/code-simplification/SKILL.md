# 代码简化：降复杂度，不改行为

简化的目标不是更少的行数，是**更容易读懂**的代码。每次简化都过一个测试："新人理解这个版本比原版更快吗？"

## 常见复杂度来源与简化动作

| 复杂度信号 | 简化动作 |
|---|---|
| 重新发明标准库/既有工具函数 | 删掉，换用现成的 |
| 深嵌套 if/循环 | 提前返回（guard clause）、提取函数 |
| 一个函数干三件事 | 按职责拆函数（每件事一个名字） |
| "以防万一"的配置项与泛化 | 删——第三个使用场景出现时再泛化 |
| 复制粘贴后微调的多份相似代码 | 合并为一个带参数的实现 |
| 绕来绕去的透传包装 | 删包装层，直接调用 |

## 纪律

1. **行为完全不变**是硬前提：简化前后跑同一套测试，结果必须一致。
2. 一次简化一类问题：先删死代码 → 再合并重复 → 再降嵌套——混着来容易引入行为变化。
3. 每步独立提交，commit message 写清"简化了什么、为什么等价"。
4. 评审视角自问："这段是删了概念，还是把复杂度挪了个位置？"——搬家不算简化。

## 抗模式

- 为省行数牺牲可读（嵌套压成一行链式调用不是简化，是加密）。
- 借简化之名改行为、顺手加功能——那是功能变更，走它自己的流程。
- 给无法验证等价的代码做"简化"（没有测试就先补测试，再简化）。
