# ONBOARDING V2 — 安装体验升级：从「装上了」到「可用、可证明」

> 来源：2026-09-30 新电脑装机实测反馈四项（用户）。
> 状态：设计 v1（待 A0 过线后排期，建议作为 DELIVERY-V2 之后的「安装体验 v2」里程碑，合计约 2 周）。
> 关联：`docs/DELIVERY-V2.md`（渠道交付形态）、`docs/MIGRATE.md`（v0.6.0 环境迁移）、产品规划 v1.4 §2.2（首发=L1 技能包）与 §9 核心指标（首用成功率 / 次周留存）。

## 四项反馈 → 四个工作流

| # | 反馈 | 工作流 | 一句话方案 |
|---|---|---|---|
| 1 | Qoder/WorkBuddy 等成熟 agent 已有可视化技能市场，原生安装更易用 | **W1 市场共存（Marketplace Bridge）** | 逆平台的文件部署改为双轨：市场项出「清单卡+深链」，asp 只部署市场装不了的判断层 |
| 2 | MCP 授权繁杂，装了包但不可用；希望凭据安全跨机迁移 | **W2 凭据钱包 + Doctor** | `asp doctor` 流量灯体检（实测才算绿）+ `asp auth export/import` 加密凭据钱包 |
| 3 | 装完没有直观证据说明环境包带来了什么 | **W3 首装对照（First-Run Proof）** | 装前基线探测 → 装后同题复测 → before/after 对照报告 |
| 4 | 安装命令/prompt 由 agent 自执行时，弱模型（Luna/HY3 类）不鲁棒 | **W4 零决策安装（Zero-Decision Install）** | 智能进脚本、模型降级为传声筒；弱模型 CI 矩阵作发版门槛 |

四项共同指向同一条主线：**把交付终点从「文件落盘」推进到「实测可用 + 可感知差异」**——直接服务首发核心指标首用成功率。

---

## W1 市场共存（Marketplace Bridge）

**问题**：重运营 agent（Qoder/WorkBuddy/Trae 等）已内建庞大的插件/技能/连接器市场，用户在其原生 UI 里装技能比 asp 的文件落盘更直观。asp 若在这些 agent 上坚持纯文件部署，是在逆平台习惯而行，安装成功率与用户信任都受损。

**方案：适配器增加内容分发双轨能力。**

1. **能力位**：`adapters/<agent>.json` 增加 `"skill_channel": "file" | "marketplace" | "both"`。市场型 agent 走新路径，文件型（Claude Code/Codex/ZCode/opencode/DSH/Kimi）维持现状。
2. **marketplace_map**：registry 维护「pack 内条目 ↔ 各 agent 市场条目」映射（skill/插件 id、发布者、深链、装后配置要点）。v1 范围：Qoder / WorkBuddy / Trae / Cursor 四家的 top pack。
3. **市场清单卡**：对市场型 agent，asp 产出有序安装清单卡（装什么→为什么→深链→装后配置），并入 DELIVERY-V2 的本地 UI picker 逐项打勾；用户在原生市场完成安装（享受其原生更新管线）。
4. **职责切分**：asp 仍负责市场装不了的部分——AGENTS.md 工作流/规则、prompts 库、MCP 配置、gold 判断标准。这部分恰是市场不供给的「方法层」。
5. **核验闭环**：`asp doctor` 增加市场项核验（配置痕迹启发式检测，不可检测的出手动勾选）；周更时提醒市场侧有新值得装的条目。

**定位重申（对外话术同步更新）**：市场解决「单个 agent 内的发现与安装」；asp 解决「同一套专业方法层跨 10 个 agent 一致生效 + 每周策展更新 + 判断标准（AGENTS.md/prompts/gold）」。市场越成熟，跨端一致性的稀缺性越高——W1 让 asp 从市场竞争者变为市场之上的策展层。

## W2 凭据钱包 + Doctor（可用性体检）

**问题**：MCP 授权流程繁杂；「明明装了技能包但还不可用」；换机时已授权的凭据希望安全迁移。

### (a) `asp doctor`——流量灯体检（v1，先做）

- 安装完成自动运行；对每个 pack × MCP 依赖出四色面板：
  - ✅ **可用**：实测调用一次该 MCP 的廉价工具，「配置了」≠「可用」，绿灯必须来自实测；
  - 🔑 **缺 key**：粘贴即写入正确位置（config/env，按 adapter 规则）；
  - 🔗 **需 OAuth**：给出深链，完成回车继续，循环至全绿（把 N 项授权压缩成顺序点击流）；
  - 🧩 **缺运行时**：给官方安装命令，不静默替装（沿用既有零破坏原则）。
- 可随时重跑 `asp doctor`；周更后只复检变更项。
- doctor 结果即 W3 对照报告的「可用性面板」数据源。

### (b) `asp auth export / import`——凭据钱包（v1.5）

- **范围最小化**：默认只导出已装 pack manifest 声明的凭据项（`mcp_requires`），导出前列明内容清单由用户确认。
- **加密**：用户口令经 Argon2id 派生密钥，AES-256-GCM 加密为单个 `.aspvault` 文件；口令永不存储。
- **传递规则（硬编码进产品）**：vault 永不经过 asp 服务端/registry，用户自行携带（U 盘/安全通道）；导入成功后可选 `--burn` 销毁源文件；vault 自带 7 天过期，导入时强制校验。
- **OAuth 分类处理**：token 缓存为可移植文件的直接迁移；机器绑定类（DPAPI/keychain 加密）标记「不可迁移」，自动转入 doctor 的深链重授权清单——诚实告知 + 把残余摩擦压到 N 次顺序点击，而不是假装能迁。
- **完成定义**：导入后自动跑 doctor，全绿才算迁移成功。
- **红线**：不上传任何数据（沿用 asp 隐私原则）；导出动作在本机完成，不依赖网络。

## W3 首装对照（First-Run Proof）

**问题**：装完环境包没有直观证据说明它带来了什么差异；「我装了环境包」不可感知。

**方案：安装即证明——装前基线、装后同题、对照报告。**

1. **probe 任务**：每 pack 自带 `probe/task.md`（一个固定小任务，如 PM 包：「以下是 3 条用户反馈与一个功能提案，判断该不该做并给出优先级」）+ `probe/checklist.json`（方法信号清单：是否命中框架、结构化输出、追问澄清、引用 skill 名等）。
2. **装前基线探测**：adapter 已知各 agent 的 headless 调用（`claude -p` / `codex exec` / `zcode -p` 等），安装前先跑一次 probe。GUI-only agent 走手动粘贴模式（asp 打印题目→用户粘贴→回收结果）。
3. **装后同题复测**：环境包生效后再跑一次。
4. **对照报告**（HTML+md，存 `asp-reports/<日期>-firstrun.html`）：
   - ① 安装矩阵：agent × 内容 × 落位路径 ✅/⚠️；
   - ② MCP 绿灯面板（复用 doctor 数据）；
   - ③ before/after 并排 + 方法信号命中 checklist + 一行结论（如「装后命中 6/8 信号，装前 1/8」）。
5. **成本守卫**：每 agent ≤2 次模型调用；`--skip-demo` 可跳过；无 headless 通道时手动模式兜底。
6. **复用**：历史报告库 = 续费价值证据（衔接「更新历史=价值证据」设计）；真实对照录屏 = 商品页主图素材（衔接「终端演示 GIF」获客资产）。

## W4 零决策安装（Zero-Decision Install + 弱模型鲁棒门）

**问题**：安装命令/prompt 交给 agent 自己执行时，弱模型（Luna/HY3 及免费 mini 类）会：改错 URL、跑错 shell、跳过哈希校验、在报错时编造步骤或反复追问。

**核心原则：把智能放进脚本，把模型降级为传声筒。** 模型做的决策越少，弱模型越鲁棒。

1. **固定三行指令**：用户拿到的 agent 指令是固定模板，唯一变量是安装码。模型职责只有两件事：原样跑这一条命令、读出最后一行。零选择、零解析、零决策。
2. **脚本硬化清单**（承 DELIVERY-V2 的脚本侧）：
   - 自检 OS/shell（PS5.1/PS7/bash 全兼容），单入口；
   - 版本 + sha256 锁定；幂等可重跑；非交互（选项全走环境变量/参数）；
   - 瞬时失败内部重试退避，不交给模型处理；
   - 输出协议机器可读：进度单行；末行固定 `REPORT: <路径>` + `STATUS: OK|FAIL`；
   - 失败只打印**短支持码**（如 `E-3F27`）+ 一句恢复指引；绝不打印堆栈、绝不进入交互——弱模型会在堆栈上发散。
3. **`asp verify`**：装后自检命令，输出二值 PASS/FAIL——弱模型只需转述一个词。
4. **CI 弱模型鲁棒矩阵（发版门槛）**：把用户实际拿到的原始 prompt 直接喂低阶模型（Luna / HY3 / 免费 mini）× shell（PS5.1 / PS7 / bash）× 干净容器，断言：退出码 0、报告存在、零追问、重试 ≤1 次。**矩阵不通过阻断发版**（与产品规划 §4.3 发布回归门同思路，把「行为变更须验证」延伸到安装链路）。
5. **兜底阶梯**：脚本连续失败 2 次后，在输出里打印「请把以下原样转给用户」+ 手动三步 + 支持码——弱模型只需照抄转发；终极兜底 = 安装页二维码/短链（完全无模型参与）。

## 排期建议与依赖

| 顺序 | 工作流 | 工作量 | 理由 |
|---|---|---|---|
| 1 | W4 零决策安装 + 弱模型矩阵 | 1-2 天 | 保护 D13 交付核心（安装码链路）；测试矩阵成本极低 |
| 2 | W2-doctor 流量灯体检 | ~2 天 | 直接消灭「装了不可用」抱怨；是 W3 报告的数据源 |
| 3 | W3 首装对照 | 1-2 天 | 信任证明 + 售前素材；依赖既有 headless 调用知识 |
| 4 | W2-vault 凭据钱包 | 2-3 天 | 安全设计需谨慎，放后 |
| 5 | W1 市场共存 | 2-3 天 + 持续维护 map | 战略项；清单卡并入 DELIVERY-V2 UI picker |

合计约 2 周，作为 DELIVERY-V2 实施后的「安装体验 v2」里程碑；均待 A0 过线后启动。

## 指标（对齐核心指标：首用成功率 / 次周留存）

- **首用成功率**：装完 5 分钟内跑出第一个好结果的比例（W3/W4 直接服务）；
- **doctor 全绿耗时**：新机从安装完成到 MCP 全绿的分钟数（W2）；
- **对照报告信号命中率**：装后 vs 装前方法信号差值（W3，也是商品页素材的量化钩子）;
- **弱模型矩阵通过率**：发版门槛 100%（W4）；
- **市场清单核验率**：市场型 agent 上清单项实际安装比例（W1）。
